03 · scaffolding

One plan. Rules, structure, and validation at every level.

A real project is too large to implement in a single pass. You decompose it into components: the core project, phases (data processing, primary + secondary analyses), and specific tests (with specific rules). The individual units. You can create scaffolding for each level, with its own governance and its own kind of validation. Markdown files carry the plan, skills carry repeatable procedures, hooks enforce the fine rules, tests prove the individual pieces. The master plan is necessary but never sufficient: like any complex build, it takes specialists at every level who know the plan yet follow rules specific to their role.

Validation by level
L1Project
Does it all run and reproduce?
Run the whole project start to finish. Does it rebuild every result? Do the components work together?
L2Module
Hand-off checks
Does each step give the next the variables/data it needs? Does the quality check pass before moving on?
L3Unit
Tests, ranges, provenance
Tests on a single function. Range checks. A tag on every number saying where it came from. A sign-off pause before anything slow or hard to undo.
Scaffolding = defining the specialist's toolkit
markdownthe plan each specialist reads before acting
skillsa specialist's repeatable, named procedure
hookssmall rules that run on their own, on every save
testsa readable report showing the pieces still fit
Examples
Validation is not a final step

It is a property of every level. A unit test means nothing if the module design is wrong; a passing pipeline means nothing if the units were never checked. You validate at every level and the check is different at each.
