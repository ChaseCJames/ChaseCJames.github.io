01 · standards

Standards are what every project + session inherits.

Standards are the documents and machinery implemented within every project and the resources a fresh agent session inherits before it does anything. They make the lab's commitments legible to humans and machines in the same place. Where workflows describe what to do for a specific kind of work, standards describe what is always true.

when standards conflict, the more specific one wins. deviations are noted explicitly.

01.2 Machinery — hooks, skills, pipelines, memory click each to expand an example
hardwired implementation in a flexible AI tool framework
Persistent mechanisms that fire across sessions. Warrant heavier review than declarative rules.
01_hooks Fire automatically on events. Lint, redact, log, attach provenance. Deterministic, cheap, visible, reversible. ▸
Example: A pre-session hook that checks any script flagged for HPC submission for [assumed] parameter tags and pauses with a summary — "3 assumed parameters found: line 14 (decay rate), line 22 (threshold), line 41 (burn-in). Confirm before submitting." The human sees the flags; the script doesn't run until they respond.
02_skills Named, reusable capabilities. A daily-notebook skill walks modified files and emits a per-project summary. ▸
Example: /lab-notebook — run at end of day. Walks all files modified in the session, extracts decisions and outputs, writes a dated entry to docs/lab_notebook/YYYY-MM-DD.md: what changed, what was decided and why, what to pick up next session. Takes ~30 seconds; produces an audit trail that actually gets written.
03_api_workflows Long-running, non-interactive pipelines with checkpoints. The agent writes; deterministic code runs. ▸
Example: A multi-step HPC pipeline: agent generates a SLURM script with provenance tags → human reviews and signs off → agent submits → agent polls for completion → agent parses outputs and writes a summary → results saved to results/YYYY-MM-DD_run/ with a manifest. Each step is a checkpoint; the human can inspect or intervene at any stage.
04_memory Dated planning notes and lab-notebook entries. Dense enough to be useful, light enough to actually get written. ▸
Example: docs/planning/2026-05-26_model_calibration.md — created at start of session. Records: goal for this session, parameters in play (with sources), what changed from last run and why, what to watch for in results. Written by the agent from the conversation, reviewed by the human before saving. Becomes the context a fresh agent session reads on day 2.
Parameter provenance tags inline, per parameter

Track where every decision in your code came from. Did you choose a parameter yourself? Does it have a literature source? Was it fitted to data — and if so, by what method? Or did the agent choose it based on your conversation? These tags make that visible at a glance.

[literature]Value from a cited source; include author + year.
[fitted]Fit to experimental data; note which dataset and fitting method (e.g. MLE, least squares, Bayesian posterior).
[assumed]No source; agent judgment — flag for human review before any long-running job.
[agent-chosen]Deliberate agent decision; reasoning stated nearby in the script.
[user-specified]Explicitly provided by the human during the session.
!
Pre-flight gates

Before any long-running script — an HPC submit is the canonical example — the agent shows purpose, parameters, expected outputs, and provenance flag count, then pauses for human signoff.
